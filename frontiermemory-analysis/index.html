Research note · November 2026 · FrontierMemory audit

Why agent memory barely helped

We read the failures—not just the final scores—to find out where useful experience disappeared.

Technical reportMarkdown sourceData & code

The short version

Suppose an AI agent can learn from other agents' mistakes. We gave it about 750 records of earlier work, had it turn those records into notes, and handed those notes to an agent facing new tasks. You'd expect fewer repeated mistakes. But the agent barely completed any more tasks.

We read what the agents actually did, rather than stopping at the final scores. Two things kept happening. Agents missed clues already in the current task, often in a file or email they never opened. And when a task needed a lesson from the past, the memory writer often left it out. Making the surviving notes easier to see helped on certain checks, but couldn't fix everything.

Central point: A fact can exist in an old run and still never reach the agent. It must be found, saved, shown, and used before it can change an answer. Even then, the whole task may fail on something else.

1. The experiment

FrontierMemory tests a simple idea: can an agent do better if it remembers what other agents learned? An earlier run is a trajectory—a record of what the agent was asked, what files or tools it used, and what happened. We used the public Hermes /learn flow to turn about 750 such records into notes, then ran the new tasks in Hermes with a local Qwen3.8-27B model. We did not use Letta Dream, the benchmark's default private generation system.

2. Why we changed how we counted failures

Our first analysis tried to give every failed attempt one reason. That sounds tidy, but it hides what happened. An agent could overlook an email, forget a version bump, and produce buggy code in the same attempt. If we checked for a “task problem” first, the whole attempt got that label—even when missing memory also mattered.

That's why we withdrew the claim that 287 of 385 failures were unrelated to memory. It reflected the order of our questions, not evidence that better memory couldn't have helped.

So we went one level smaller. Each task has individual requirements: save a file at the right path, use the right calculation, include an example, bump a version. We grouped the grader checks into 73 distinct requirements (72 scored), and 57 were missed at least once. If the same requirement is missed in ten separate attempts, that's ten missed requirement instances, but still only one type of requirement. Keep that distinction in mind for the graphs.

3. The overall score barely changed

Without memory, the agent completed 6 of 45 attempts. With the three generated sets of notes, it completed 7, 4, and 8. On average, the difference was roughly one percentage point—not reliable evidence of an improvement (p = 0.50).

Here's the catch: a task only passes when every check passes. A note can fix four mistakes, but if the agent still makes a fifth, the task gets zero. We need to look beneath the all-or-nothing scores.

4. Did the task already contain the answer?

For each missed requirement, we asked: Was the answer somewhere in the task the agent had right now? It might be in the prompt, a repository file, an email, or a tool result. If so, we call it a task-information miss. If the task didn't provide it, it's a missing-knowledge miss—the kind of gap that older experience might fill.

Of the 57 distinct requirements that were ever missed, 38 had information available in the current task and 19 did not. Those numbers describe types of requirements, not failed attempts.

A task-information miss is not proof of model incapability

On market share, the right calculation method was in an email thread. All five successful attempts read that thread; none of the 25 failures did. That may reflect search, source-selection, time allocation, or reasoning—not a demonstrated inability to do the calculation.

In the no-memory arm, the agent met 53/60 directly stated requirements, but only 16/39 requirements requiring search or choosing among sources. That's evidence of a difficulty gradient, not a clean diagnosis of “incapability.”

Limit: We searched the old records already knowing what failed. Some “available” lessons were inferred from related tasks rather than written as exact answers. A writer without that hindsight might not find them.

6. What went wrong while writing the notes?

This is one of the strongest trace-level findings. Our generator was Hermes /learn running on Qwen. It could inspect the earlier corpus, but the inspection procedure it actually carried out left large portions unread or incorrectly parsed.

Only the first message was extracted

Maintainer conventions often appeared later in conversations. Runs 1 and 3 mainly extracted each file's first user message; Run 4 kept the first and last. None of the writers printed a maintainer follow-up from the multi-turn runs. The Awilix version-bump convention lived there.

Different log formats were mishandled

In Codex-formatted trajectories, an environment preamble appeared before the actual request, so extraction sometimes selected the wrong turn. Run 1's OpenCode extraction returned empty text. Run 3's parser classified 137 files as unknown.

Sampling and truncation cut off the lesson

Run 1 printed three examples per group at 500 characters. Its Word2Vec passing example was cut before the correct empty-input fallback. Run 4 truncated lines before details needed for another task's scoring method.

The wrong examples were explored—or trusted

No writer inspected Brightpath or Eurogrid trajectories beyond prompts and tool-name counts. Run 1 kept a partnership rule from a failed prior attempt, even though a passing prior attempt contradicted it.

What we can say: the combined Hermes /learn + local Qwen generation process often failed at ingesting experience. We cannot isolate a software defect in Hermes itself from the model's choices while operating it.

But more visibility doesn't create a lesson that wasn't saved. If the release-tier rule never entered the files, pasting all those files into the prompt still wouldn't add that rule. The agent might infer it independently—that's a different route, not successful memory retrieval.

8. The agent read the note. Why did it still fail?

There's a crucial distinction between complete memory and partial or misleading memory. In the observed trials, every requirement with a fully covering note that the agent read or had pasted was met: 60/60. That's reassuring, but it covers only a handful of Word2Vec and DAPT requirements; selection also matters because the agent chose when to open files.

Where notes only partly covered a requirement, or led the agent in the wrong direction, the requirement still failed in 30 of 89 cases where such a note was opened or pasted. But 8 of those 30 are DAPT failures, and the newer investigation found the agent's answer on that specific check was supported by the capture. Excluding DAPT, the report gives 22 failures out of 81 opened partial/misleading-note exposures. That is a descriptive count, not a causal rate of memory misuse.

DAPT is not evidence that the agent ignored a correct no-scan instruction. The notes warned against inferring a scan from port count alone, and the agents observed additional evidence: an actual rapid SYN sweep. The checker expected “no scan” using unavailable thresholds. In partnership, by contrast, a stale “approval of record governs” note pointed away from the latest email. Similar mistakes sometimes happened without memory, so we cannot assign all blame to the note.

9. Four examples of what actually happened

Word2Vec: memory revealed the contract

Task: build a text pipeline. Hidden expectation: put the callable in /workspace/solution.py with the right function signature. Without memory: no control or placebo trial met the path requirement. With real notes or records: every arm did. The remaining empty-input behavior still failed some attempts.

Awilix: agents noticed the tier but didn't bump the version

Task: implement a feature and follow an internal release tier. Expected: set package.json to 12.1.0. Observed: 0 of 30 attempts in either variant changed the version file. In the explicit variant, 20/30 mentioned the tier, and some discussed versioning yet deferred to release tooling. One even wrote a v12.1.0 changelog heading without changing the version. The rule was consistent with ten past maintainer runs but never entered the notes. Crucially, those prior runs gave the bump as an explicit later instruction; the held-out task required the agent to act unprompted.

Market share: the answer was inside the task

Task: calculate a business metric. Right method: defined in a mail thread. Observed: all five passes opened that thread; all 25 failures didn't. Many agents searched “market share,” while the email subject used “market-share.” This is a current-task discovery problem, not necessarily missing historical knowledge.

DAPT: an actual scan, but the checker expected “no scan”

Task: interpret network-capture metrics. Observed: all 30 agents identified a SYN sweep of 1,000 destination ports on one target and answered that a scan occurred. The checker's own comment defines scanning as more than 500 ports on one target. Yet its reference pools that traffic with a much larger SSH session, diluting port entropy and the SYN-only fraction; it then reports “no scan,” and hard-codes the traffic as benign. The secret thresholds were in skill files omitted from this task. Three attempts failed only this check. Memory still helped with several other DAPT metrics, but the remaining zero passes are partly a specification problem, not simply failed memory use.

10. Where did the 65 successes come from?

Across all ten arms, 65 attempts passed. On 45 of those passes, the current task contained everything required, though some agents still opened memory. On 14 Word2Vec passes, agents had read or been shown real notes or earlier records. The other 6 passed cattrs or cookie-store requirements without reading a known covering source.

11. Five stubborn checks—and five different explanations

Five distinct requirements were missed in every one of their 30 relevant attempts. They blocked five tasks from passing in any arm: two Awilix version bumps, customer delivery's runnable failure example, DAPT's port-scan verdict, and Eurogrid's calculation. Those are 150 failed task attempts, not 150 unique requirements. The new investigation inspected every one of those 150 requirement-trials and found that the reasons are substantially different:

All five checks were missed in 30/30 relevant trials, but that does not make them equivalent memory failures. Evidence: full investigation with source passages and 150 per-trial classifications.

There was also a sixth task (the ChatGPT proposal) with no full passes, despite each of its individual checks being met at least once somewhere.

Could perfect memory solve everything? No evidence supports that. If we hypothetically supplied every fact absent from each task without changing failures on information already accessible in the task, the report's conditional ceiling is only 13–19 passes of 45, depending on the arm. Better pointer memories might also help the task-information problem; the ceiling does not test them.

Two evaluation defects are documented, with different consequences. DAPT: its expected port-scan answer contradicts the task's own criterion and observed capture. That affected the check in all 30 trials and was the only remaining failed check in three attempts. Eurogrid: the correct rounded team-method answer is 243,275.57, but its gold/reference shows .56 and fails the positive criterion. This Eurogrid defect affected the reference, not the agent outcomes: every agent selected the wrong calculation. Other reference scores of zero are setup artifacts, not evidence that a task was impossible.

Finally, don't mistake the “task information accessible” label for “stated clearly in the prompt.” Across the mixed arms, most such missed instances required searching or choosing sources; the report also explores stricter labels. Only one local model and harness were tested, with three attempts per task per arm, and many comparisons are noisy.

12. What I would take away

The best-supported story isn't “agents ignore memory” or “memory is useless.” It's more specific:

  1. Previous experiences often held useful knowledge, but the writer didn't ingest or preserve much of it. Its transcript parsing, sampling and truncation created observable losses.
  2. When a relevant, fully covering note survived, making it accessible helped on the requirements it addressed. That effect is concentrated in Word2Vec and DAPT.
  3. Many other misses involved information accessible inside the current task. More factual memory didn't consistently fix search, source selection, and execution.
  4. Improvement at the requirement level often disappeared in the all-or-nothing task score. DAPT shows why, but its never-met port-scan requirement is itself a benchmark specification defect.

One economical follow-up: rerun only memory generation with a reliable reader for all trajectory formats and turns, holding Hermes/Qwen fixed. Compare writer exposure and note coverage before considering costly downstream task reruns. A separate agent-capability experiment would still be needed to prove which task-information misses are unsolvable rather than undiscovered.

Bottom line: Memory is only useful if the original evidence is available, the writer captures it, the agent encounters it, and the agent can use it in the current task. This audit shows losses at several links, with the largest upstream loss in the observed memory-generation process and a persistent task-side discovery problem. The follow-up investigation also shows that a few persistent failures arise from where agents place work or how a benchmark defines correctness, not missing reasoning alone.
