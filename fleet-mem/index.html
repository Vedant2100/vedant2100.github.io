Selecting Earlier Task Records for Coding Agents

An exploratory study of two different decisions: what to retain from earlier repository work before future tasks are known, and what a later coding agent should actually see.

TL;DR

A coding agent working on a new issue may benefit from an earlier issue in the same repository. But two decisions are easy to conflate: should the earlier record be retained at all? and, after a new task arrives, should that record be shown to the worker?

This pilot separated those decisions on ten SWE-ContextBench-derived target tasks. A custom source-only selector made one retain/drop decision for each earlier record without seeing any future target. A fixed retriever later considered the three most recent records for each target, and an optional target-aware selector could expose or withhold the surviving records.

8 / 10targets where the benchmark-annotated related record reached the fixed top-three retrieval set
2 / 8of those related records survived source-only admission
1 / 8was ultimately exposed by the later read filter

The end-to-end result was not a memory win. The separately executed No-Memory condition resolved 2/10 targets, while Share-All, Random admission, source-only selective admission, selective admission plus read filtering, and the known-related diagnostic each resolved 1/10. The selective-write condition fixed more designated failing tests on some tasks, but did not resolve more tasks.

That result needs careful interpretation. The stored “memories” were not verified lessons learned by successful earlier agents: they were shortened historical issue records plus paths touched by a reference change. 197 of 211 records were truncated and all 211 had unknown source-agent outcomes. Independent worker runs also disagreed even when their prompts were byte-identical. One of the two No-Memory successes exists only after a separate test-path-filtered regrade of a raw patch that had not applied.

Main takeaway: this experiment is most informative as a failure analysis of information selection and experimental design. It shows exactly where benchmark-related history disappeared—retrieval, source-time admission, then target-time exposure—but it does not establish that those exclusions were correct, that memory is harmful, or that the tested selector improves coding performance.

1. The Question

Persistent agent memory is often discussed as if “store useful experience” and “retrieve relevant experience” were one problem. They are not.

A source-time decision happens before the future task exists. It asks whether an earlier record is sufficiently bounded, reliable, and reusable to retain. A target-time decision happens later, after the new issue is known. It asks whether an already-retained record belongs in this worker’s context.

Every worker run starts from a clean target repository state. The goal is not to build a new memory database; it is to make the two selection points measurable against executable software outcomes.

2. A Real Example from the Pilot

The cleanest example comes from Django. An earlier task, django__django-16910, concerned QuerySet.only() interacting incorrectly with select_related() on a reverse OneToOneField. The record stored by the experiment was:

Stored source record: “Earlier task experience concerned: QuerySet.only() doesn't work with select_related() on a reverse OneToOneField relation. Description On Django 4.2 calling only() with select_related() on a query using the reverse lookup for a OneToOne relation does not generate the correct query. All the fields from the related model are still included in the… Its reference change touched: django/db/models/sql/query.py.”

A later task, django__django-35356, reported a related failure involving recursive OneToOneField relationships together with select_related() and only(). The benchmark annotates the earlier task as related to the later one.

This example is useful precisely because it did not end in a success. The earlier record survived every selection stage and reached the worker, yet the later task remained unresolved. The experiment cannot tell whether the record was insufficient, the worker failed to use it, or the relation was useful only in a richer representation than the stored card.

The converse also occurred. The earlier SymPy record sympy__sympy-16988—about duplicate handling in Intersection and touching sympy/sets/sets.py—entered the top-three history for later related tasks but received DO_NOT_SHARE. That single source decision was reused across three later targets. Once rejected, no later target-aware selector could recover it.

3. Building a Pilot Where Selection Was Actually Non-Trivial

The substrate was SWE-ContextBench Lite: 300 earlier “experience” tasks, 99 related target tasks, and published source–target relationships. Those published relationships were kept hidden from ordinary retrieval and selection. Instead, each target received every strictly earlier task from the same repository as its historical candidate pool.

All 99 targets were screened before agent treatments. The automatic audit separated clean temporal relationships from explicit prior references, high-hint cases, same-PR/co-resolution cases, and ambiguous chronology.

The eleven frozen histories contained 603 target–record entries that deduplicated to 211 unique source records. The ten primary histories contained 188 of those records, but source-time admission remained frozen over the full 211-record universe. The primary target pools ranged from 13 to 114 earlier same-repository records.

The ten primary target IDs correspond to only eight distinct resolving pull requests: two pairs of SymPy targets share a PR. The pilot also spans only three repositories. Those dependencies matter when interpreting “10 targets” as a sample size.

4. What “Memory” Actually Meant in This Experiment

This is the most important qualification in the study.

The completed pilot did not use fresh trajectories from earlier coding agents. Each source record was produced deterministically from benchmark metadata:

  • up to roughly 320 characters from the earlier issue description;
  • the earlier task’s creation time and repository provenance;
  • up to eight paths touched by the source task’s reference change;
  • a generic warning to inspect current code and tests rather than treat the record as a prescription.
211unique historical records in the frozen source-decision universe
197 / 211records whose stored description ends in a truncation marker
211 / 211records with unknown source-agent outcome

The paths came from reference changes, not from an observed successful source-agent trajectory. The timestamp used for chronology was the released issue created_at, which is reproducible but does not prove that the corresponding repair or experience existed at that exact time.

So the experiment tests selection over historical task records—not validated learned lessons. A failure to benefit from these records is not evidence that richer agent memory, verified repair summaries, or successful source trajectories would also fail.

5. The Experiment That Ultimately Ran

The protocol evolved substantially while infrastructure and worker failures were diagnosed. The completed core comparison used the following six conditions on the same ten primary target tasks:

ConditionSource-time admissionTarget-time handling
A · No MemoryNo records retained for the workerNo record shown
B · Share-AllAll records availableExpose the three fixed recent slots
C · RandomRandom global subset matching the selector’s total admission countSame fixed recent slots
D · Selective WriteCustom source-only binary selectorSame fixed recent slots
E · Selective Write + ReadSame source-only selector as DCustom target-aware EXPOSE/WITHHOLD filter
F · Known-Related DiagnosticUse hidden benchmark relationship metadataShow the annotated related record(s) within the common budget

The original protocol also proposed a deliberative LLM write arm (G), but it was never run and remained outside the amended A–F core.

The selector

The selective conditions used the TypeSafe System-One API with model jev-1.13.0 through SDK 0.7.2. The source decision was a custom binary SHARE / DO_NOT_SHARE question. The later decision was a custom EXPOSE / WITHHOLD question. This is not an evaluation of the published Jev-Mem architecture; it uses the Jev System-One API as a bounded decision service.

The source selector admitted 123 of 211 records. The target-time selector was asked about 15 admitted records and returned EXPOSE once. Saved decision rationales were empty, so the archived evidence does not support reconstructing why a particular record was accepted or rejected from prose after the fact.

Fixed retrieval matters

Retrieval happened before source admission filtering: each target first selected its three most recent historical records. Admission could remove those slots, but older retained records did not backfill them. This made the write decision directly observable, but it also made global rejection unusually consequential.

The random control matched the selector’s global number of retained records, not the amount or length of context exposed on each target. And the final experiment did not include a Share-All + target-aware-read condition, so it is not a complete 2×2 write/read factorial.

The coding worker and evaluator

The completed B–E runs used Microsoft’s SWE-Edit baseline scaffold (revision 60ca673) with requested model gpt-6-luna, xhigh reasoning effort, up to 100 iterations, and an 1,800-second task budget. Every target ran from a fresh repository state. The unchanged SWE-ContextBench evaluator was executed through a project-local Apptainer compatibility layer.

Why the repository contains so many worker amendments

The execution path was deliberately preserved instead of cleaned up after the fact. Early local mini-SWE-agent runs were invalidated by command/submission-interface problems. The original Luna qualification then failed its preregistered 2-of-3 full-resolution gate: the two graded tasks were both unresolved. A planned Sol comparison never completed because of patch/application, interruption, and quota problems. Several local-model candidates produced partial coding evidence but failed operational/mechanics screens or infrastructure limits.

A later output-boundary amendment made the repository diff—not the worker’s prose or Finish marker—the authoritative prediction, and excluded test-path changes from submitted source patches. Model-free fixtures validated that boundary. A user-authorized development amendment then ran the frozen No-Memory vs known-related signal test with Luna. That test produced executable discordance on 3/10 targets, which authorized the subsequent B–E exploratory treatment run.

These amendments are part of the evidence record. They are why the final result should be read as an exploratory development pilot rather than a preregistered confirmatory effect estimate.

The dependence structure is easy to miss. Those six target-level source-admission losses are not six independent bad decisions. They arise from only two unique source records, each reused across three later SymPy targets. A global admission error—if it is an error—can therefore propagate across several future tasks.

Context quantity also changed sharply across policies:

30records exposed by Share-All across ten targets
20records exposed by Random admission
15 → 1records exposed by selective write → selective write+read

The corresponding character/4 context estimates were 9,408, 6,267, 4,752, and 315 tokens for B, C, D, and E. These are estimates rather than tokenizer-measured memory tokens. Because context amounts were not matched per target, outcome differences cannot be cleanly attributed to selection quality alone.

Selective write (D) has the largest aggregate FAIL_TO_PASS count, but that does not translate into more completed tasks. Much of the difference comes from partial progress on a small number of targets—for example, 4/6 failing tests passed on sympy__sympy-16946 while the task remained unresolved.

The 120 lost PASS_TO_PASS tests in every B–F aggregate are concentrated on sympy__sympy-21309. No-Memory preserves those tests in its separately executed run. That pattern looks dramatic, but identical-prompt evidence prevents a simple “memory caused the regression” interpretation.

The read-filtered arm’s only resolved task received no memory. E exposed zero records on nine of ten targets, including its sole resolved target, sympy__sympy-19235. The only target where E actually exposed a record was django__django-35356, and that task remained unresolved.

Run variability is not a footnote

On nine targets, E exposed zero records, making its worker prompt byte-identical to the archived No-Memory prompt. Yet independent runs sometimes produced different executable outcomes. In particular, differences on sympy__sympy-21203 and sympy__sympy-21309 show that a single worker run per condition is not enough to assign every outcome difference to memory.

The No-Memory 2/10 result has a grading-boundary caveat

The raw No-Memory prediction for sympy__sympy-21203 did not apply in its original evaluation and was unresolved. A later test-path-filtered regrade removed test-file edits from the saved patch; that sanitized patch applied and resolved the target with 3/3 failing tests fixed and 124/124 previously passing tests preserved. The reported A total of 2/10 includes this regraded success.

B–E, by contrast, were executed later with the repaired authoritative output boundary; all 40 submitted treatment patches contain no test-file edits. Therefore A and B–E are not perfectly symmetric executions, even though their canonical outcomes are all archived.

8. What the Results Do—and Do Not—Show

The tempting headline would be “memory made the coding agent worse.” The evidence does not support that claim.

What is directly observed is narrower:

  • the benchmark-related record was often unavailable by the time target-aware selection happened;
  • none of the tested memory conditions improved full-task resolution over the separately executed No-Memory baseline;
  • selective write changed partial failing-test performance on some targets;
  • the read-filtered arm mostly reduced to no memory at all;
  • independent worker runs varied enough to confound single-run causal comparisons.

Several unresolved issues prevent a stronger conclusion.

LimitationWhy it matters
No verified useful-memory positive controlThe historical record may never have contained a repair lesson capable of helping the worker.
Issue proxies, not learned agent memories197/211 records are truncated and every source outcome is unknown.
Single independent worker run per conditionPrompt-identical A/E runs sometimes disagree, so treatment and worker variance are entangled.
Different A/F grading pathOne reported No-Memory success appears only after a separate sanitized regrade.
Unequal context quantityB/C/D/E exposed 30/20/15/1 records; Random is globally count-matched, not target-context matched.
Missing Share-All + Read conditionThe independent causal effect of target-time read filtering cannot be identified.
Small dependent sample10 IDs come from 3 repositories and only 8 distinct resolving PRs.
Approximate chronologyIssue creation time does not establish when a source repair or usable experience became available.

The known-related condition is also not an “oracle upper bound.” A benchmark relationship says the earlier task is related; it does not certify that this particular 320-character record is useful to this worker. Its 3/10 executable discordance against No Memory establishes behavioral sensitivity to context, not positive transfer.

9. The Experiment Suggested by These Results

The next study should make useful information a demonstrated property of the setup before evaluating governance.

  1. Use verified source-agent experience. Generate a real earlier trajectory, record whether it succeeded, and extract a concise lesson grounded in that trajectory rather than an issue proxy.
  2. Establish a positive control first. Directly inject a known useful lesson and require repeated executable improvement on at least some targets before evaluating selectors.
  3. Repeat worker runs under one grading boundary. Use the same authoritative patch collection, same evaluator path, and multiple seeds/runs for each condition.
  4. Complete the write/read factorial. Add Share-All + target-aware Read so admission and exposure can be separated experimentally.
  5. Match context at the target level. Compare the selector against random and relevance baselines with the same number and approximate length of exposed records per target.
  6. Scale only after these checks pass. The current ten-target pilot is useful for debugging the measurement problem; it is not a population-level estimate of coding-agent memory.

The experiment did answer one useful question: where can potentially relevant history disappear? In this setup, the largest bottleneck was not target-time retrieval. It was the earlier, future-blind admission decision. Whether that bottleneck is beneficial cannot be known until the retained information is first shown to be useful.

10. Where This Sits Relative to Prior Work

The narrow framing matters because several adjacent systems already study coding-agent memory.

WorkRelevant ideaDifference here
SWE-ContextBenchTests whether prior coding context can help later related tasks.This pilot turns its relationships into hidden evaluation metadata and studies a future-blind retain decision before later exposure.
ReasoningBankBuilds reusable reasoning memories from agent interactions.The completed pilot did not use learned trajectories; it used historical issue-based records.
MemGuardStudies lifecycle control and verification for coding-agent memories.This pilot focuses on the observable source-admission → later-exposure path in a small executable task set.
Jev-MemSystem-One-controlled agentic memory and efficient retrieval.The experiment did not run Jev-Mem’s published architecture; it used custom binary decisions through the Jev System-One API.
ChainSWESequential software maintenance where repository state persists across tasks.Each worker here resets on a target task; the intervention is explicit historical context rather than accumulated repository state.

The useful contribution of this pilot is therefore methodological rather than architectural: it makes a source-only retain decision reusable across later tasks, traces exactly where benchmark-related records disappear, and exposes the controls needed before a causal claim about memory selection is credible.
