Who Gets to Remember?

Shared memory for coding-agent fleets: deciding which experiences become team knowledge, when later agents should see them, and whether those decisions improve real software outcomes.

Vedant Borkute · Fleet Mem · Research note · October 2026

TL;DR

A coding agent can finish a task with useful experience that is not fully captured by the patch: a repository convention, a testing procedure, a failure mode, or an architectural assumption. Shared memory can preserve that experience for future agents, but it can also preserve stale, redundant, overgeneralized, or misleading advice.

Fleet Mem separates two decisions: whether an experience should become shared team knowledge before future tasks are known, and whether a later coding agent should see that memory for its current task. Both decisions are evaluated with executable repository tests.

The current benchmark uses SWE-ContextBench as the software-task substrate but replaces its one-known-source setup with full earlier same-repository histories. The clean development set contains 11 later tasks with 13–114 earlier candidate experiences each. No full memory-policy result exists yet.

1. A Concrete Example

Suppose a repository keeps track of files it has already processed. Two path strings can refer to the same file:

./data/report.csv
data/report.csv

A naive program compares those strings literally, decides they are different, and processes the same file twice. An earlier coding agent encounters that bug and discovers the repository’s convention: normalize filesystem paths before comparing them.

# before
if new_path == old_path:
    ...

# after
if normalize(new_path) == normalize(old_path):
    ...

The important thing is not the exact function name. The earlier agent has learned a reusable fact about how this codebase handles file paths.

Candidate memory from Agent A: “In this repository, normalize filesystem paths before equality checks.”

Weeks later, a fresh Agent B receives a different bug: the file watcher is reporting the same file twice because two equivalent path forms are being treated as different. Agent A’s earlier lesson could save Agent B time.

But a real shared memory would not contain only that one clean lesson. It might also contain:

Jev is therefore useful as a controller, not as the novelty claim. The experiment should remain meaningful if Jev is replaced by deterministic rules or a stronger deliberative LLM. The scientific object is the controlled decision boundary between one worker’s experience and a fleet’s shared memory.

Why ChainSWE was not enough

ChainSWE initially looked ideal because later coding agents inherit an evolving repository. In practice, that same persistence made explicit textual memory difficult to isolate: code, tests, and repository state already carried much of the useful information.

14 / 36No shared memory resolved
12 / 36Share-all resolved
12 / 36Governed resolved

More importantly, only seven targets contained multiple candidate memories, and clear conflict or supersession cases were rare. The controller therefore had little meaningful choice.

Benchmark lesson. Sequential tasks are not enough. The benchmark must create a non-trivial pool of earlier experiences while hiding which ones will matter later.

3. Benchmark Design

The current benchmark returns to SWE-ContextBench but changes how its source-to-target relationships are used. The original relationship remains hidden metadata; it no longer chooses what the later coding agent receives.

For each later task, Fleet Mem gathers all eligible earlier experiences from the same repository. The current clean development set has 11 later tasks, each with 13–114 earlier candidates.

13–114 candidates"] A2["Earlier task C"] --> POOL A3["Earlier task D"] --> POOL A4["Earlier task E"] --> POOL POOL --> G["Share / do not share"] G --> MEM["Shared memory"] MEM --> R["Show / withhold"] R --> T2["Later task"] end style MEM fill:#e1f5fe,stroke:#039be5,stroke-width:2px
Figure 3: SWE-ContextBench’s known relation becomes hidden evaluation metadata. The live system instead operates over the full eligible repository history.

A strict temporal boundary prevents future information from leaking into the share decision. When an earlier experience is converted into memory, neither the extractor nor the share controller may see the later task, hidden tests, reference patch, later commits, or eventual memory effect.

A parallel construction using SWE-rebench V2 tested a more natural history-first benchmark. It produced 48 later tasks across 12 repositories, 226 earlier episodes, and 600 history links. The histories were richer, but relation quality and evaluator readiness were not sufficient: chronology depended on issue/PR creation time, useful links were difficult to establish, and only 1 of 48 targets passed both no-fix and reference-fix evaluator controls. That path is deferred rather than discarded.

4. Experimental Design

The main experiment separates two decisions. At source time, the system chooses share / do not share. At later task time, it chooses show / withhold. The source-time decision is made once and cannot depend on which future task eventually arrives.

ConditionWhat the coding agent seesWhat it isolates
No memoryNo earlier lessonsBaseline
Share everythingEligible earlier lessons under a fixed budgetCost of indiscriminate sharing
Random, matched amountA random subset with the same count/token budget as governed memorySmart selection vs simply less context
Selective sharingOnly memories approved before future tasks are knownValue of the source-time decision
Selective showingBroad memory bank, filtered for the later taskValue of read-side filtering
Selective sharing + showingBoth stages controlledFull system
Strong reasoning controllerSame decisions made by a stronger LLMQuality vs cost/latency
Known-relevant experienceThe benchmark’s linked earlier experience is supplied directlyWhether useful memory can move the worker at all

The final row is deliberately tested first. If a known relevant earlier experience cannot change executable outcomes, there is no useful memory signal for a more elaborate controller to recover.

The candidate-memory extractor is held separate from the governor and is expected to capture candidate lessons broadly. Otherwise extraction itself would quietly perform the selection being evaluated.

5. Current Status

0completed memory-policy conclusions

The benchmark-construction stage has passed its structural check. A routing smoke test confirmed that the infrastructure can create different memory exposures, but that is not a governance result.

The remaining pre-treatment question is coding-worker suitability. GPT-6 Luna failed the original 2-of-3 full-resolution qualification rule. Its actual patches nevertheless showed partial competence: on a SymPy task it fixed one of two failing tests but introduced a severe performance regression; on a Django task it fixed the reported duplicate-column case, fixed one of six failing tests, and preserved all 166 previously passing tests.

The current sequence is therefore: compare Luna and Sol on the same already-used development tasks, freeze one worker, then compare no memory against the known-relevant earlier experience. The full governance comparison proceeds only if that simpler test establishes a measurable memory effect.

Current boundary. Fleet Mem does not yet show that shared memory improves coding-agent performance. The present evidence establishes the benchmark structure, executable evaluation path, and experimental controls needed to test that claim.

Methodological controls

The worker and memory policy are not tuned simultaneously. Future-task information is not used to write memories. The share decision is made once before later tasks are known. The task set is not changed after memory outcomes are observed. Broken-harness or empty-patch runs are not interpreted as memory results.

Natural history and stress cases

The primary benchmark uses natural repository histories. A secondary stress set may include duplicate advice, over-broad memories, failed-source lessons, stale or superseded guidance, conflicts, and superficially similar but wrong guidance.

Already-institutionalized knowledge

A lesson may already be encoded in implementation, tests, documentation, comments, configuration, or CI. Such cases are tracked because declining to create redundant textual memory can be the correct organizational decision.
